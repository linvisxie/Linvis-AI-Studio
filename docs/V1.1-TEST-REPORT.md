## 一、剪映集成：为什么上一轮失败，这一轮成功

本机剪映 **11.7.0.14652**（`D:\JianyingPro\11.7.0.14652`）。
上一轮会话尝试了 7 种组合（T-PLAIN / T-ENC / T-PATCH / T-FINAL / T-NATIVE-TPL / T-CLONE / T-ASIS）
全部失败，并把原因归结为「必须破解 11.7 加密」。**这个结论是错的。**

### 1.1 根因定位（二进制证据）

分析 `VECreator.dll` 的 `DraftLoadVerifier` 字符串表，校验链是：

```
verify_draft
  ├─ check_draft_json_valid  → parse_json_failed   ← 明文走这条
  ├─ check_load_result       → decrypt_failed      ← 密文走这条
  ├─ check_app_support       → from_unusual_path
  └─ check_version_support   → lowAppVersion       (最低 71.0.0)
```

关键：`parse_json_failed` 与 `decrypt_failed` 是**并列分支**，不是先后依赖。
明文 JSON 只要能解析，就根本不会进入解密分支。**所以不需要解密。**

上一轮失败的真实原因是三个具体错误：

| 错误 | 后果 |
|---|---|
| 用 `draft_info.json`（pyJianYingDraft 默认名） | 11.7 只认 `draft_content.json` → 判「内容已损坏」 |
| 用 `new_version: "143.0.0"`（库默认） | 远超当前版本 → `lowAppVersion` |
| 缺 `Timelines/<id>/` 多时间线结构 | 结构不完整 |

### 1.2 加解密为何在独立进程里必然失败

`.venv-jy` 里 pyJianYingDraft 的 `JianyingDraftCrypto` 对 11.7 的表现：

```
encrypt_bytes(b'{"a":1}')  → 成功，56 字节
decrypt_bytes(上面自己的输出) → 失败：ok_flag=True, output_len=0
decrypt_bytes(剪映真实密文)   → 失败：ok_flag=True, output_len=0
isFileEncrypted(剪映真实密文) → False
```

DLL 连自己刚加密的数据都解不开，`isFileEncrypted` 对真密文返回 False —— 说明
加密子系统在这个进程里根本没初始化。`VECreator.dll` 里 `draft_encryption_params`
结构含 `entropy_dynamic` / `first_block` / `is_unlocked`，证明 11.7 用的是
**会话级动态熵**，静态调用拿不到正确密钥。

**结论：不要试图在进程外解密 11.7 草稿。写明文，让剪映自己去加密。**

## 二、中文口播链路

### 2.1 修复的问题

**问题 1：faster-whisper 完全不可用**

```
TypeError: open() got an unexpected keyword argument 'metadata_errors'
```

原因：faster-whisper 1.2.1 的 `audio.py` 调用 `av.open(..., metadata_errors="ignore")`，
但项目 `.venv` 装的是 PyAV 19，该参数已被移除。

修复：`.venv` 降级 `av==13.1.0`。

**问题 2：CUDA 缺失导致引擎降级**

`cublas64_12.dll` 不存在，但 ctranslate2 报告 `get_cuda_device_count() == 1`。
且错误在 `transcribe()` **返回的惰性生成器被迭代时**才抛出，不在调用处。
原代码只在构造 `WhisperModel` 时做回退，所以永远回退不到 CPU。

修复（`engine/py/transcribe.py`）：把生成器物化（`list(segs)`）纳入 try，
并在此处回退 CPU。

**问题 3：模型快照不完整**

`models--Systran--faster-whisper-small` 缺 `model.bin`（只有 config/tokenizer）。
已从 `hf-mirror.com` 补全 483,546,902 字节。

## 三、侧链压缩（口播 ducking）

实现：`engine/lib/sidechain.mjs`，用 FFmpeg `sidechaincompress`。
以配音为 key 信号压缩 BGM，不改变人声本身。

```bash
node engine/bin/linvis.mjs duck <project> --compare
```

### 实测数据

输入：配音 8.16s + BGM 8s，参数 `threshold=0.05 ratio=8 attack=20ms release=400ms`

| 指标 | ducked | flat（未压缩） |
|---|---|---|
| 整体响度 | -21.61 LUFS | -20.44 LUFS |
| 峰值 | -6.49 dBTP | -5.43 dBTP |

逐帧（约 0.1s）RMS 对比，共 96 帧：

- **76/96 帧音乐被压低**
- 平均压低 **-1.93 dB**
- 最深压低 **-9.68 dB**（出现在人声最强的帧）
- 最大值 0.0 dB（无人声的帧不压）
- 压低深度与人声强度正相关 → 说明是跟随而非固定衰减

`--compare` 会额外输出 `.flat.wav`（同样两轨但不压缩），用于人工 A/B 试听。

## 四.5 修掉的两个隐蔽缺陷（自查发现）

初版完成后我按任务书逐条复核，发现两处「看起来能跑但其实不合格」的地方，已修复：

### 缺陷 1：素材没有复制到草稿目录

初版只在草稿里写**绝对路径**引用 `projects/<id>/assets/...`。
任务第六节明确要求「复制素材到草稿目录，保证引用有效」。
后果：工程目录一旦移动或临时文件被清理，草稿素材全部失效。

修复：统一复制到 `<草稿>/media/`，改为草稿内相对路径。已实测：

```
D:/剪映/剪映草稿/JianyingPro Drafts/LV-SMOKE7/media/PLACEHOLDER-voice-zh.wav
```

### 缺陷 2：骨架携带源草稿身份，会导致「草稿列表异常」

初版复制骨架时保留了 `draft_meta_info.json`（加密，内含源草稿的 `draft_id`）
与 `draft_cover.jpg`、`.backup/`、旧时间线目录。

后果：剪映会把新草稿认成源草稿，弹出「草稿列表异常 — 检测到部分草稿丢失」，
关闭时还可能把内容写回**用户的原始草稿**。这正是上一轮 `T-ASIS` 失败的真正原因。

修复：复制骨架时剔除以下文件/目录，让剪映首次打开时自己重建身份：

```
draft_meta_info.json / draft_meta_info.json.bak / draft_cover.jpg
draft_content.json.bak / .backup/ / deepagent/ / 旧时间线目录
```

已实测：剔除后剪映正常打开，并**自动重建了自己的** `draft_meta_info.json`。

### 顺带修掉的 schema 缺漏

`project.json` 的 `audio.layers[]` 之前不允许 `role` 字段（`additionalProperties: false`），
导致 `duck` 命令所需的 `role: "voice"|"music"` 无法写进配置。
已在 `engine/schema/project.schema.json` 补上 `role` 枚举。

## 四.7 补齐「动画镜头进剪映」缺口（本轮新增）

### 问题

之前 `linvis render` 一次性渲染整条视频，产出一个完整 mp4。
剪映草稿需要**每个镜头一个独立素材文件**才能逐轨编辑，
所以纯动画镜头（`impact-title` / `cold-open` / `dissolve` / `reveal-question`）
在草稿里只能保留文字层——画面轨是空的。

底层 `renderComposition()` 早就支持 `frameRange`，但 CLI 从未暴露，
适配器也拿不到片段文件。

### 实现

新增 `linvis scenes <project>`（`engine/lib/render-scenes.mjs`）：

1. 按 `scene.from` / `durationInFrames` 切帧区间
2. bundle 一次，复用 `serveUrl` 逐个渲染（比每镜头单独 bundle 快得多）
3. 输出 `out/render/scenes/<projectId>/<序号>-<sceneId>.mp4`
4. 适配器自动扫描该目录，按 sceneId 建立索引并作为画面轨素材

### 三个实现要点

| 要点 | 说明 |
|---|---|
| frameRange 是**闭区间** | Remotion 上界包含，且合法帧号 ≤ `durationInFrames-1`。要把半开区间 `[from, to)` 转成 `[from, to-1]` 并在末尾夹住。**第一次跑时 s5 就栽在这里**（报 `frame range 180-285 is not inbetween 0-284`） |
| 每段必须带音轨 | 否则剪映里音画错位。区间内没音频就渲成静音轨——这是正确行为，不伪造 |
| 不做响度归一 | 片段是「素材」不是「成片」。每段各自归一会导致拼接处音量跳变 |

### 实测结果

## 六、已知坑（给后来者）

1. **剪映打开草稿时会占住目录**，`--force` 覆盖会 EPERM。
   适配器检测 `.locked` 并给出明确提示，而不是抛栈。
2. **`draft_meta_info.json` 是加密侧车**，改它会与 `project.json` 冲突。
   正确做法是复制骨架后整份沿用，只换时间线 ID。
3. **PowerShell 脚本可能被 Defender 拦截**（`ScriptContainedMaliciousContent`）。
   已有可用的 `out/jy-test/shot2.ps1`；新写脚本可能被拦。
4. **截图坐标换算容易错**：`shot2.ps1` 默认输出 1100×619，全屏 1920×1080，
   scale = 1920/1100。用错比例会点空。
5. **判断草稿是否真被打开，用 `.locked` 文件，不要靠截图。**
